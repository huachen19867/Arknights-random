### 可复用结论

项目目录起步时只有 `材料/背景.jpg` 和 `材料/大概样式.png`。前者是 2:1 的编队界面批注截图，后者是纵向干员卡片参考；两者都包含截屏或批注成分，应作为设计参考保留，不能直接当成可发布 UI 素材。

PRTS 移动端“干员一览”无需运行页面 JavaScript即可拿到干员基础信息。页面的 `#filter-data` 下有连续的 `<div>`，关键属性为 `data-id`、`data-zh`、`data-profession` 和 `data-rarity`。`data-rarity` 是从 0 开始的内部值，显示星级必须加 1。2026-08-01 实测解析总数为 423；各星级数量为 1 星 11、2 星 5、3 星 17、4 星 61、5 星 195、6 星 134；八职业数量合计同样为 423。

PRTS 立绘可按 MediaWiki 文件规则计算：对 UTF-8 文件名做 MD5，前 1 位和前 2 位作为目录。文件名优先 `立绘_{名称}_2.png`，失败后回退 `_1.png`。原图可能超过 5 MB，不宜整库直接打包；已验证 800px thumb 后追加 `?image_process=format,webp/quality,Q_80` 可显著降低体积，同时保留透明背景。适用边界是 PRTS 当前媒体服务和缩略图规则；同步脚本仍需把 404、规则变化和图片缺失当成可恢复错误。

飞书知识库链接解析为 Docx 节点“设置界面的示例”，正文只嵌入一块画板。画板明确了星级与职业默认全选、人数 1–12 默认 12，以及独立 ban 干员页。知识库适合作为项目文档容器；若要结构化维护数据，应在知识库中放 Base，并由构建脚本导出静态快照，而不是让公开前端直接访问飞书 API。

### 飞书返回结构与解析坑点

`lark-cli base +record-list` 在当前版本可能返回二维矩阵：`data.fields` 是列名，`data.data` 是行矩阵，`data.record_id_list` 是对应记录 ID。不能只兼容 `items[]`。全量导出必须按 offset 串行分页，并同时处理 `has_more`、`total` 和“返回数等于 page size”的兼容信号；空页却仍有 `has_more=true` 应立即失败，避免无限循环。

飞书 URL 样式文本读回时可能是 `{ link, text }`、数组，也可能是 Markdown 形式 `[文本](url)`。解析 Markdown 时不能用只匹配到第一个右括号的正则，因为阿米娅形态页 URL 本身含括号；当前做法是定位 `](` 后取到字符串最后一个 `)`，保留 URL 内部括号。

成功信封判断必须使用 `ok === true` 或进程退出码 0，不能沿用旧 OpenAPI 的 `code === 0`。临时 JSON 参数写到 `scripts/.tmp` 后必须在 `finally` 中删除；错误输出只提供阶段、目标资源和可执行修复提示，不回显凭证。

### 战斗技能的真实边界

不能按星级硬推技能数，也不能假设所有干员都有 1–3 个技能。PRTS 实测夜刀和 Castle-3 的“技能”章节明确写“该干员没有技能”，芬有 1 个，史尔特尔有 3 个。全库 423 名的 0 / 1 / 2 / 3 技能分布为 `16 / 17 / 255 / 135`。解析器缺少“技能”标题时必须报错；标题存在但既没有技能小节、也没有明确“该干员没有技能”时同样报错，不能把页面结构漂移静默发布成 `skills: []`。严格规则已用 `--recheck-skills` 强制抓取 423 个详情页通过。

`skills: []` 表示详情页已经核验且确实无战斗技能；完全缺少 `skills` 字段表示旧快照或 Base 尚未核验。这两个状态必须贯穿 PRTS 种子、Base 导出、前端类型和卡片文案：前者显示“无技能”，后者显示“技能未收录”。只提取详情页“技能”章节，不得误抓后面的“后勤技能”。技能名从每个 `技能N` 小节的名称节点解析，并用夜刀、芬、史尔特尔等真实页面做样本检查。

飞书 Base 因此新增 `技能1`、`技能2`、`技能3` 三个普通文本字段和 `技能已核验` 复选框。三列全空且核验为真才导出 `skills: []`；核验不为真时省略字段。技能编号必须从 1 开始连续，不能填写技能1、技能3而留空技能2。技能四字段是单独的人工数据组，通用 `--update-existing` 不覆盖，只有 `--update-skills` 显式接受 PRTS 技能差异。

### 官方新增与稳定 ID

PRTS `data-id` 不是所有形态都唯一，且职业、名称都可能变化，不能每次根据当前字段重算 ID。`scripts/data/prts-operators.json` 同时作为稳定 ID 登记表：先按原始 `prtsId` 分组，优先用名称+职业精确继承，再尝试同组内名称唯一匹配（忽略职业），之后才在无歧义时用同职业或单旧/单新记录继承；只有新增实体分配原始 ID、`prtsId:职业`、`prtsId:名称` 或序号后缀。已有 `R001:术师` 等值以后视为不透明主键，即使职业变化也保持不变；歧义导致旧 ID 消失时由 removal guard 中止，不猜测。回归测试覆盖了阿米娅三形态中单个形态改职业仍继承旧 ID。

每次 PRTS 同步输出 `scripts/data/prts-diff.json`，默认拒绝任何旧记录消失，并限制单次新增和字段变化各不超过 50。未变化记录复用旧技能、符合条件的精二 URL和旧 `updatedAt`；数据集级 `generatedAt` 可以变化，记录级时间只在业务内容变化时更新。这样第二次真实同步得到 add 0、remove 0、change 0、unchanged 423，Base 也不会因抓取时间制造 423 条伪差异。

### Base 限流与可恢复写入

初次技能回填预览确认 423 条差异只涉及技能1–3、技能已核验和同步时间，其他字段差异为 0。飞书在连续完成两个 200 条批次后，对第三批返回 `the method：OpenAPIBatchUpdateRecords limited`；前 400 条已经成功，重跑预览只剩 23 条，证明差异驱动写入可安全恢复。随后按剩余差异补齐，最终 Base preview 为新建 0、更新 0、差异 0。

这个响应不一定只表现为早期已知的 `1254291`。`runWriteWithRetry` 现只对 `1254290`、`1254291`，或错误信封明确包含 `OpenAPIBatchCreateRecords/OpenAPIBatchUpdateRecords limited`、`rate limit`、`too many requests` 时指数退避；其他错误不泛化重试。默认批次降为 100，批次间隔 1200ms，仍保持同一表串行。出现部分成功时先重新 preview，让幂等差异定位剩余记录，不能盲目重放原始 423 条。

### 精零立绘迁移的实际起点

现有 [sync-prts.mjs](../scripts/sync-prts.mjs) 的 `portraitCandidates()` 按 `立绘_<名称>_2.png`、`立绘_<名称>_1.png`、头像顺序探测，且把 `_2` 标为 `elite2`、把 `_1` 标为 `elite1`。这里的 `elite1` 命名不准确：PRTS 的 `_1` 是初始立绘，精英化 0 和精英化 1 共用，应在新模型里统一叫 `elite0` 或 `initial`。当前种子分布是精二 390、所谓 `elite1` 33，因此切换会是一轮预期中的全库立绘变化，而不是普通增量更新。

精零策略应把 `_1.png` 作为唯一正式立绘候选；头像只作为是否允许发布的产品兜底，不能再静默回退到 `_2.png`，否则会重新混入老板已经否决的精二构图。建议默认精零 URL 不可用时直接让同步失败并报告干员，确认确实存在特殊个体后再明确增加例外表。`resolvePortrait()` 的错误文案、统计名 `reusedElite2`、同步日志、`inferPortraitKind()`、数据校验统计、README 和测试夹具都要同步改名，不能只调换候选数组顺序。

旧的复用条件只认可 `previous.portraitKind === 'elite2'` 且 URL 等于预期精二地址，迁移后必须改为只复用 URL 完全一致的精零地址。第一次执行需要全量 HEAD 校验；以后无变化同步才允许复用。全量变化会触发 `diffOperatorVersions()` 的大批变更保护，DS 应使用一个语义明确的一次性迁移参数或迁移脚本，而不是永久放宽默认 `--max-changes`。迁移报告必须确认全部变化仅涉及 `portrait`、`portraitKind` 和必要的记录级 `updatedAt`，干员 ID、名称、星级、职业、技能均不得意外改变。

Base 是正式人工维护源，不能在 PRTS 同步后直接覆盖。顺序应为：本地生成精零种子与差异报告；全量检查 URL 和数据自检；运行 Base preview 并确认差异范围；只有明确写入时才使用现有受保护的立绘更新通道；最后从 Base 重新导出 `public/data/operators.json`。现有写入条件是 `--update-existing --update-portrait-url`，必须先预览 `scripts/data/base-diff.json`，再按最多 100 条一批、批次间隔至少 1200ms 串行写入并处理方法级限流。写完后重跑 preview 应为 0 差异，Base 导出与精零种子应逐字段一致。不要手改生成的 JSON，也不要覆盖“启用”和“立绘附件”。

### 模组数据的建议模型

战斗技能有官方硬上限 3，所以当前 Base 使用技能1–3固定列；模组数量会随官方持续增加，不应复制成“模组1–3”并写死上限。推荐在同一 Base 内增加子表“干员模组”，一行一个模组，至少包含：稳定的模组ID、干员ID、模组名称、分支/类型代码（页面有可靠值时才填）、展示顺序、启用、来源URL、同步时间。原“干员数据”主表增加“模组已核验”复选框，用于表达三态：子表有记录且已核验表示已收录；子表无记录且已核验表示该干员当前确实没有模组；未核验表示未知。不要用一条虚假的“无模组”子记录表示空数组。

网页快照建议仍把数据聚合回干员对象，最小形状为 `modules?: Array<{ id: string, index: number, name: string, code?: string, sourceUrl?: string }>`。`modules: []` 表示已核验且确实无模组，缺少 `modules` 字段表示未知，与现有 `skills` 的语义保持一致。`id` 优先继承 PRTS 模组详情链接中的稳定标识；如果页面没有可靠 ID，应把“干员稳定 ID + 页面模块标识”作为不透明主键并建立增量登记，不能只用数组序号，因为官方新增或调整展示顺序时序号会变化。名称、代码和顺序是版本化字段，名称变化不能导致旧模组 ID 无提示丢失。

若 DS 判断当前 lark-cli 的跨表读取与关联字段会显著拖慢 MVP，可先把“干员ID”做普通文本外键，脚本严格校验它必须存在于主表；不要退回全局多选字段，也不要把整段 JSON 塞进主表作为长期人工维护界面。子表 token/table ID 应写入 `config/feishu-base.json` 的结构化配置，只保存资源标识，不保存凭证。

### PRTS 模组解析边界

在 [operators.mjs](../scripts/lib/operators.mjs) 增加独立 `parsePrtsModules(html)`，沿用技能解析的防漂移原则：先定位详情页的“模组”章节并截断到下一同级标题，只从该章节提取模组，不得误抓天赋、后勤技能、模组任务、升级材料或 Stage 1–3 效果文本。当前产品只需要可供选择的模组实体与名称，不需要模组数值、解锁任务、材料和等级效果。

不要在没有真实页面证据时假定 HTML 选择器、模组最大数量或“无模组”提示文案。DS 应先人工检查并保存/构造至少三类固定夹具：明确无模组、恰好一个模组、两个或更多模组；锁定当前 PRTS 的预期名称和稳定标识，再实现解析。只有章节明确表达“暂无/没有模组”时才接受空数组；章节缺失、结构存在但解析不到实体、重复 ID/名称、空名称或无法建立稳定 ID都应报错停止，不能把页面漂移静默发布成 `modules: []`。在线样本检查可覆盖三类真实干员，但核心单元测试仍应使用固定 HTML 片段，避免 PRTS 内容更新让解析器测试失去可解释性。

同步脚本应像技能一样支持复用已核验模块和显式 `--recheck-modules` 全量复查，并把 reused/fetched 计数写入控制台及差异报告。新增干员、模块字段未知、干员详情发生相关变化时抓取详情；未变化记录复用旧 `modules` 并保留原 `updatedAt`。模组应加入 `VERSIONED_OPERATOR_FIELDS`、`validateDataset()`、自检统计和 removal/change guard。一次正常的无变化重跑必须得到 add 0、remove 0、change 0，不能因为抓取时间制造全库伪差异。

### Base 同步、导出与验收顺序

Base 写入沿用“人工维护源、默认只预览”的原则。建议为模组建立独立 preview/write 通道，不与 `--update-existing` 或 `--update-skills` 混写；主表的“模组已核验”和子表增删改作为一个逻辑数据组生成差异报告。默认只新增缺失模组并报告已有差异；更新、停用或删除必须显式授权。官方页面暂时移除某模组时不得直接物理删除 Base 行，优先报告并把删除保护停住，由人工判断后将“启用”改为否或确认删除。任何写入仍需批次不超过 100、同表串行、限流退避、可幂等恢复。

导出器要先读主表，再读模组子表，按稳定干员 ID 聚合；必须拒绝孤儿模组、重复模组 ID、未知干员 ID、同一干员重复顺序、未核验却已有歧义数据，以及已核验但解析不完整的记录。前端类型可以先接收 `modules` 而不展示，避免数据准备与 UI 决策耦合。正式快照发布前至少验证：423 名现有干员数量和稳定 ID 不变；全部正式立绘为 `_1.png` 精零策略或经书面记录的特殊例外；精二计数为 0；模组 unknown 计数为 0；模组数组内 ID 唯一、顺序连续、名称非空；Base 导出与 PRTS 种子的精零立绘和模组差异为 0；数据自检、前端单测、生产构建与桌面/手机视觉检查全部通过。

`portraitCandidates()` 现在只生成 `立绘_<名称>_1.png`（kind `elite0`）和头像探测 URL。`resolvePortrait()` 按 800px thumb → 原图 URL → 例外回退 → 报错的顺序处理。复用条件只认可 previous.portraitKind === 'elite0' 且 URL 与预期精零地址完全一致。首次迁移用一次性参数 `--migrate-portraits-elite0`：只允许 portrait/portraitKind/modules 三个字段变化（modules 是首次采集），跳过 `--max-changes` 保护，其余字段变化一律报错；迁移报告统计 migratedPortraitCount。

### PRTS 模组章节的真实结构与解析规则

有模组干员的详情页“模组”章节第一个 h3 总是“XXX证章”（basictemplate，只有证章图，不是可选模组），后续每个模组一个 h3，实体区块是 `equiptemplate`，文本首行形如 `<模组名称> <类型码> <模组名称> 调整效果...`。无模组干员（1–3 星及部分 4 星）整页没有“模组”章节——注意**整页可能在其他上下文提到“模组”**（Friston-3 的天赋说明引用了“浊心斯卡蒂Y模组”），所以“页面含模组字样”不能作为无模组判定的反信号，只以章节 id 是否存在为准。

解析规则：`<span id="模组">` 不存在 → 返回 `[]`；存在但解析不到模组实体、类型码缺失或重复 → 报错。证章判定是“标题含‘证章’且区块无 equiptemplate”——标题可能是“阿米娅证章（近卫）”这种带形态括号的形式，不能只用 `/证章$/`。类型码用“标题后 200 字符内匹配 `[A-Z]{2,5}-[A-Z\u0391-\u03c9]`”提取，注意 `BLA-Δ` 这类希腊字母类型码：JS 的 `\b` 词边界把 Δ 当非单词字符，第二个 \b 会失配，要用负向前瞻 `(?![A-Z0-9\u0391-\u03c9-])` 代替。

防漂移闸门：`--recheck-modules` 全量复查时，若 previous.modules 非空但本次解析为空，直接报错，避免 PRTS 结构漂移把有模组干员静默变成无模组。模组 ID 用“干员稳定 ID + 分支类型码”（如 `R001:医疗:INC-X`），不用数组序号（官方调整顺序会变）。模块字段加入 VERSIONED_OPERATOR_FIELDS、validateDataset（数组内 ID 唯一、index 从 1 连续、名称非空、上限 30）、自检统计和迁移报告。

## 2026-08-01｜Base 迁移写入与随机模组开关

### Base 初始化与写入的实操坑

主表加“模组已核验”复选框用 `lark-cli base +field-create --json '{"name":"模组已核验","type":"checkbox"}'` 成功；子表“干员模组”用 `+table-create --fields [...]` 创建成功。但三个坑必须记录：
