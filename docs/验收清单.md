# 明日方舟干员随机抽取工具验收清单

更新日期：2026-08-01

本清单用于实现完成后的独立验收与后续 AI 交接。`[ ]` 表示必须通过实际操作、自动化测试或构建产物验证，不能把“代码看起来存在”视为通过。P0 是核心交付门槛，任一项失败均不能宣称核心功能完成；P1 是首版质量项，应完成或在交接文档中明确说明取舍。

## 一、需求基线与冲突裁决

需求证据按以下优先级解释：老板最新明确纠正 > 老板原始需求 > 飞书画板 > 两张材料图 > 早期实现方案。发生冲突时以更高优先级为准。

已锁定的两项纠正如下：

- P0：右侧主按钮可见文字必须精确为“开始抽取”。不能出现“开始行动”，也不采用材料图批注中的“开始随机”。
- P0：飞书多维表格 Base 是干员数据的人工维护源，不再只是“可选人工覆盖层”。网页运行时仍读取由 Base 导出的静态快照，不直接携带凭证访问飞书 API。

本次审计已只读核对以下证据：

- `材料/背景.jpg` 为 2760 × 1256 的主界面参考，包含 2 行卡位、右侧纵向操作区和红色批注；红色批注及原截图控件不是发布素材。
- `材料/大概样式.png` 为 321 × 583 的纵向干员卡参考，核心信息是干员图、名称，并带星级与职业视觉信息。
- 飞书节点“设置界面的示例”在 2026-08-01 读取到 revision 11；画板原始节点明确含有两个“默认全选”、人数“1~12，默认12”、“随机技能 是/否”，以及“ban 干员”点开新页面并通过稀有度、职业定位干员的说明。
- 飞书 Base“干员库”的“干员数据”表有 13 个字段：干员ID、名称、星级、职业、启用、立绘URL、来源URL、同步时间、技能1、技能2、技能3、技能已核验、立绘附件。2026-08-01 最终导出为 423 条启用记录、0 条空白、0 条未启用、423 个唯一 ID、0 个空立绘 URL、0 个未知技能，并与 PRTS 正式种子关键字段差异为 0。

## 二、P0 核心功能验收

### 2.1 首次打开与页面结构

- [x] 首次打开直接进入抽取主界面，无需飞书登录或其他账号登录。
- [x] 桌面宽屏下结果区为 2 行 × 6 列，共 12 个固定卡位；抽取少于 12 人时未使用卡位保持明确的空槽状态。
- [x] 右侧存在醒目的纵向主按钮，按钮可见文字精确为“开始抽取”。
- [x] 全项目可见 UI 文案中不再把该按钮称为“开始行动”或“开始随机”。
- [x] 设置入口、Ban 干员入口、返回抽取页的路径都可点击且浏览器刷新后不会进入不可恢复页面。

### 2.2 设置页

- [x] 无本地历史设置时，1–6 星全部选中。
- [x] 无本地历史设置时，先锋、近卫、重装、狙击、术师、医疗、辅助、特种全部选中。
- [x] 星级和职业均支持多选，界面能区分选中与未选中状态。
- [x] 抽取人数可在 1–12 之间调整，步长为 1，首次默认值为 12，界面同步显示当前数值。
- [x] 保存或离开设置页后，抽取页使用当前星级、职业和人数，而不是只改变视觉选中状态。
- [x] 星级或职业全部取消时不会崩溃；抽取页进入“无可用候选”状态并给出可执行的恢复提示。
- [x] “随机技能”使用互斥的“是/否”控件，默认“否”；旧版 localStorage 缺少该字段时迁移为关闭，其他设置不丢失。
- [x] 随机技能设置保存后立即影响下一轮抽取，刷新页面后保持。

### 2.3 Ban 干员独立页

- [x] Ban 干员是独立页面或独立路由，不是挤在普通设置项里的不可展开长列表。
- [x] 页面展示从正式 Base 快照导出的全干员库，而不是少量硬编码示例。
- [x] 支持按中文名称搜索，并支持用星级、职业标签定位干员。
- [x] 可添加和取消单个 Ban；重复点击或重复保存不会产生重复 ID。
- [x] 支持清空全部 Ban，批量操作结果可见且可逐项取消。
- [x] 返回设置页或抽取页后 Ban 立即生效，被 Ban 的 ID 不进入候选池。
- [x] Ban 使用稳定的干员ID持久化，不以可能改名的中文名称作为关联键。

### 2.4 筛选与随机抽取

- [x] 候选池严格等于“启用的 Base 快照记录 ∩ 已选星级 ∩ 已选职业 − Ban ID”。
- [x] 选择单一星级后，结果中每名干员均为该星级；职业筛选和组合筛选以同样方式验证。
- [x] 一次抽取结果按干员ID去重，绝不为了凑人数重复同一干员。允许不同轮次再次抽到同一干员，除非后续另有需求。
- [x] 请求人数不超过候选数时，结果数量精确等于请求人数。
- [x] 候选数少于请求人数时，展示全部候选且每人仅一次，并明确提示“请求 N 人，当前仅 M 人可用”或等义信息；不能静默重复、补入不符合筛选的干员或假装抽满。
- [x] 候选数为 0 时展示空结果和恢复指引，例如调整星级、职业或 Ban；不能抛出未处理异常。
- [x] 随机索引由 `crypto.getRandomValues` 或等价的无偏安全随机实现产生，不能回退到 `Math.random`；随机 API 不可用时应显示可理解错误。
- [x] 连续快速点击“开始抽取”不会造成多个动画和结果相互覆盖；抽取期间重复触发被忽略。

### 2.5 随机技能

- [x] 开启后，每名抽中干员从自己的真实 `skills` 数组独立、安全随机一个技能；不按星级臆造技能数。
- [x] 技能选择发生在点击“开始抽取”时并写入本轮结果对象，不会因 React 重渲染改变。
- [x] 关闭后不生成、不展示技能选择；再次开启只影响后续抽取。
- [x] `skills: []` 作为已核验无技能显示“无技能”；缺少 `skills` 字段作为未知显示“技能未收录”，两者都不重抽干员。
- [x] 全库真实分布为 0 / 1 / 2 / 3 个技能 `16 / 17 / 255 / 135`，夜刀、Castle-3、芬、史尔特尔样本检查通过。

### 2.6 结果卡片

- [x] 每张非空卡片至少显示干员立绘和中文名称，且信息来自同一条 Base 导出记录。
- [x] 卡片同时清楚表达星级和职业；职业不能只靠颜色区分。
- [x] 透明立绘采用保持比例的 contain 类布局，不因统一裁切丢失头部或名称区域。
- [x] 图片加载失败时卡片仍显示名称、星级、职业及占位视觉，不导致整页布局坍塌。
- [x] 新一轮抽取结果完整替换上一轮结果；结果状态使用可读提示，技能信息进入卡片 aria-label。

## 三、P0 飞书 Base 与数据管线验收

### 3.1 Base 作为维护源

- [x] 配置只保存 Base、数据表和字段映射等非密钥标识；用户 access token、app secret 等凭证不进入 Git、前端源码或构建产物。
- [x] 导出脚本按真实 Base token 和 table ID 读取“干员数据”表，并处理分页，不能只导出默认第一页。
- [x] 导出只接纳“启用”为真的正式记录；完全空白的 Base 占位行可跳过，部分填写但缺少必填字段的行必须报告为错误，不能静默丢失。
- [x] 必填字段至少为：干员ID、名称、星级、职业、启用；技能维护另含技能1–3和技能已核验。星级只能是整数 1–6，职业只能是八大职业之一，干员ID必须非空且全表唯一。
- [x] 技能1–3与技能已核验作为独立数据组；三列全空且已核验导出 `skills: []`，未核验时省略 `skills`，技能编号存在空洞时导出失败。
- [x] “启用”为空时的语义必须在 README 和代码中一致。建议按未启用处理；从 PRTS 写入的新正式记录必须显式写入 true。
- [ ] “立绘附件”作为人工覆盖时，构建脚本将附件下载为可发布的本地静态文件；不能把需要飞书鉴权或会过期的临时 URL 写进网页快照。
- [ ] “立绘附件”和“立绘URL”同时存在时有确定且记录在文档中的优先级。建议附件优先、URL 次之；多个附件的处理规则也必须确定并产生警告。
- [ ] 在 Base 中修改一名干员的名称、星级、职业、启用或立绘后，重新导出并构建，网页出现对应变化；这是证明 Base 确为维护源的必要端到端用例。

### 3.2 PRTS 初始化与更新

- [x] 提供可重复执行的 PRTS → Base 同步命令，用 `data-id` 做幂等 upsert；重复执行不会重复创建同一干员。
- [ ] 同步器自动识别并清理 Base 创建时产生的全空占位行，清理前后报告数量；只允许删除所有业务字段均为空的行，半填写记录必须保留并报错，不能被当作空行误删。
- [x] PRTS 的 `data-rarity` 写入 Base 前加 1，并校验最终范围为 1–6。
- [x] 同步器只接受八大职业，设置明确 User-Agent、超时、低并发、缓存与有限重试。
- [x] 人工在 Base 中维护的字段是否会被 PRTS 再同步覆盖，必须有明确策略和命令开关。至少“启用”和“立绘附件”不得在普通更新中被无提示覆盖。
- [x] 2026-08-01 的已知基线为 PRTS 可解析 423 名干员。初次全量同步后，应核验 Base 中存在 423 条非空且干员ID唯一的正式记录、0 条全空占位行；若 PRTS 当前总数已变化，必须给出新总数、与 423 基线的差异及校验报告后再决定是否接受，不能硬凑 423。
- [x] 同步先生成临时结果并完成校验，再更新 Base 或正式快照；失败时保留上一份可用数据，并以非零退出码结束。
- [x] 上一版种子作为稳定 ID 登记表；官方新增、新形态、改名或改职业不会重算已有 ID，歧义与旧记录消失默认中止并输出 `prts-diff.json`。
- [x] 无内容变化的同步保留旧记录 `updatedAt`；连续两次真实同步得到新增 0、删除 0、变化 0、未变 423。

### 3.3 Base → 静态快照

- [x] 提供 Base → `operators.json` 的单独导出命令；网页运行时不请求 PRTS 页面或飞书。当前立绘为无需鉴权的 HTTPS URL，本地化尚未实现。
- [x] 快照中每条记录只包含前端需要的字段，至少为 id、name、rarity、profession、portrait；不包含 Base record token、附件鉴权信息或本机绝对路径。
- [ ] 正式快照通过重复 ID、空名称、星级范围、职业枚举、图片存在性和总数突变校验后才替换旧快照。
- [x] 最终完整数据的空立绘 URL 数为 0；单张远端图片失败时网页有文字占位。
- [x] 正式构建不连接飞书也可运行和抽取，因为快照已进入静态产物；远端立绘完全离线不保证加载。
- [x] 正式快照加载失败时应用显示明确的数据错误或“示例数据”标识；少量 fallback 数据不能冒充正式全干员库。
- [x] “技能已核验”为真时导出连续的技能数组，包括合法空数组；未核验时保留为未知而不把整条干员记录判无效。

## 四、本地状态验收

- [x] 星级选择、职业选择、抽取人数、随机技能和 bannedIds 保存在带版本号的 `localStorage` key 中。
- [x] 修改上述设置后刷新页面，状态保持不变；关闭并重新打开同源站点后仍保持。
- [x] 第一次访问或存储项不存在时恢复“星级全选、职业全选、人数12、随机技能关闭、Ban为空”。
- [x] `localStorage` 中出现损坏 JSON、越界人数、未知星级、未知职业、重复或过期 Ban ID 时，应用进行归一化并继续可用。
- [x] 隐私模式、容量限制或禁用存储导致读写抛错时，本次会话仍可抽取。
- [x] 本机偏好不写入共享 Base；Base 只维护公共干员数据。

## 五、视觉与可用性验收

- [x] 主界面保留参考图的浅色工业感、2 × 6 编队感和右侧纵向操作区，但不直接把 `背景.jpg` 当页面底图，也不出现红叉、批注气泡、原游戏返回键或删除键截图。
- [x] 卡片参考 `大概样式.png` 的纵向层级重新绘制，干员图和名称是主要视觉信息；不能把整张参考图当通用卡框叠在所有干员上。
- [ ] 1366 × 768 与 1920 × 1080 下，12 个卡位和“开始抽取”按钮均可见、可操作，重要文本不互相遮挡。
- [x] 390 × 844 等窄屏下主卡组采用明确的内部横向滚动，Ban 页采用两列布局，不把 12 张卡压缩到无法辨认。
- [ ] 主按钮、设置、Ban、筛选控件均可通过键盘访问，有清晰焦点态和可读名称；纯图标按钮必须有 aria-label。
- [x] 文本和关键控件对比度可辨；选中状态同时有 INCLUDED/EXCLUDED、ACTIVE/OFFLINE 等文本，不只依赖颜色。
- [x] 抽取动效不会阻塞操作，且在 `prefers-reduced-motion: reduce` 下关闭或显著缩短。
- [x] 页面清晰标注 PRTS 来源、非官方、非商业和相关素材权属说明；发布范围变化时重新核对授权边界。

## 六、异常与恢复验收

- [ ] Base 未授权、scope 不足、表或字段 ID 失效时，脚本输出目标 Base、失败阶段和可执行修复提示，且不修改正式快照。
- [ ] Base 存在重复 ID、非法星级、未知职业、半填写记录或无法下载的附件时，错误报告定位到记录 ID/干员ID/字段；批量过程不能只报“同步失败”。
- [x] PRTS 页面结构变化、404、超时或限流时，同步器有限重试后失败，保留上一次可用种子/快照，不无限请求；真实样本检查可提前发现技能解析漂移。
- [ ] JSON 请求失败、返回空数组或格式错误时网页不白屏；如果回退样例，应显眼标注非正式数据源。
- [ ] 单张立绘 404 不影响其他卡片，控制台和界面均能定位到对应干员。
- [x] 候选不足、候选为零、所有人被 Ban、星级全不选、职业全不选均有可理解提示。
- [ ] 部署到子路径时数据和图片仍能加载；禁止把 `/data/operators.json` 等绝对根路径写死为唯一访问方式，应使用 Vite base URL 或等价方案。

## 七、自动化与人工测试证据

### 7.1 自动化测试最低集合

- [x] 默认设置测试：1–6 星全选、八职业全选、人数12、Ban为空。
- [x] 设置归一化测试：人数小于1/大于12、非法枚举、重复 Ban、损坏存储均得到预期结果。
- [x] 候选池交集测试：星级、职业、启用状态和 Ban 同时生效。
- [x] 无重复测试：候选数不少于请求数时，结果长度正确且 ID 集合大小等于结果长度。
- [x] 候选不足测试：请求人数大于候选数时返回全部不同 ID，并产生可供 UI 展示的不足状态。
- [x] 空候选测试：返回空数组而不是异常或重复填充。
- [ ] Base 数据规范化测试：分页合并、空白行、重复ID、非法星级/职业、附件与URL优先级。
- [x] 路径测试：在非根 `base` 配置下，数据 URL 仍指向正确构建路径。
- [x] 随机技能测试：关闭时无技能结果；开启时 0技能、未知、1技能、多技能分别得到稳定且正确的状态。
- [x] 稳定 ID 与版本迁移测试：唯一 ID 增加新形态、改职业、删除保护、大批变化上限、无变化时间戳幂等均覆盖。
- [x] Base 技能测试：已核验空技能、未核验未知、连续技能、技能空洞和技能组独立更新均覆盖。
- [x] Base 限流测试：仅对 `1254290` / `1254291` 或明确方法级限流退避，其他错误不泛化重试。

### 7.2 人工端到端用例

- [x] 清空站点存储后打开：确认默认全选、人数12；点击“开始抽取”得到12张不重复卡片。
- [ ] 只选6星与医疗，人数设为3：结果均满足两个标签；刷新后设置保持。
- [ ] Ban 一名已知候选并连续抽取多轮：该 ID 从不出现；取消 Ban 后重新进入候选池。
- [x] 构造候选少于人数：只选 1 星得到 11 名候选，界面只显示 11 名唯一干员并准确提示。
- [ ] 在 Base 修改一条记录并禁用另一条，执行导出与构建：网页分别显示修改且不再抽到被禁用记录。
- [ ] 断网打开已经构建并由静态服务器提供的站点：仍可读取快照、显示图片并抽取。
- [x] 用 1440 × 900 和 390 × 844 检查卡片、按钮、设置页、Ban 页及错误提示；1440 × 900 正式快照实抽确认 12 张技能条无明显遮挡。
